# Запасной серверный вариант — только подготовка

## Выбор после темы

- Игра с анимацией, физикой, ИИ противников и локальным сохранением может целиком работать на GitHub Pages. «Статический» относится к раздаче файлов, а не игровому процессу.
- Общие сохранения/таблица результатов: рассмотреть Cloudflare Workers + D1.
- Небольшие общие комнаты: рассмотреть Workers + SQLite-backed Durable Objects + WebSockets.
- Постоянная тяжёлая симуляция: бесплатный Workers не считать подходящим заранее. После темы оценить нагрузку и выбрать отдельное размещение; не урезать требования молча.

Для серверного варианта удобнее разместить клиент и API вместе в Workers Static Assets: один origin, меньше настроек CORS. Pages + отдельный API тоже возможен.

## Что подготовлено

В toolchain установлен и закреплён Wrangler 4.156.0. Проверка из этой папки:

```text
npm run check:server-tools
```

Это проверка запуска CLI/runtime, НЕ тест API, БД или мультиплеера. Worker, база, комнаты, конфигурация приложения и облачные ресурсы до темы не создаются.

Обнаружена Windows 10 (10.0.19045). По документации Wrangler официально поддерживается Windows 11. `wrangler --version` и `workerd --version` запускаются, но совместимость с приложением не подтверждена. После темы сначала проверить локальный запрос к минимальному серверу. Если runtime несовместим, резерв — сборка и согласованный preview-деплой через GitHub Actions на Ubuntu. Это требует аккаунта Cloudflare и секретов; не является уже настроенным staging.

## Бесплатные ограничения (проверено по документации 30.10.2026)

Workers Free: 100 000 запросов/день, CPU 10 мс на запрос, память 128 МБ. Ожидание сети не равно CPU.
Durable Objects доступны на Free только с SQLite storage backend: 100 000 запросов/день, 13 000 GB-s/день. При исчерпании бесплатных лимитов операции завершаются ошибками. Для WebSockets использовать hibernation, где применимо. Частые серверные тики могут быстро исчерпать квоту.
Не включать Workers Paid автоматически. Квоты D1 и статических ресурсов перепроверить при выборе архитектуры.

## Внешние шаги, требующие владельца аккаунта

1. Создать/открыть аккаунт Cloudflare и оставить Workers Free; платный тариф не нужен для подготовки.
2. После выбора серверного варианта выполнить локальную авторизацию `node secure-npm.cjs exec -- wrangler login` из toolchain. OAuth проходит в браузере владельца, секреты не отправлять в чат.
3. Для GitHub Actions создать ограниченный Cloudflare API token для нужного аккаунта; сохранить в GitHub Secrets как CLOUDFLARE_API_TOKEN, account ID — CLOUDFLARE_ACCOUNT_ID. Не помещать в VITE_* или файлы.
4. Workflow сервера создать после темы под реальные bindings, миграции и команды тестирования. Сначала отдельное preview-окружение с отдельными данными, затем production.

## Проверки после появления сервера

Типы → тесты → сборка → локальный HTTP-запрос → браузер → preview. Проверить ошибки сети, недопустимый ввод, ограничения запросов, серверную проверку прав, CORS для раздельных origins. Для комнат проверить два клиента, переподключение и отсутствие утечек между комнатами. Не заменять эти проверки запуском `--version`.
