Локально закреплены Vite 8.3.5, TypeScript 7.0.2, Vitest 5.0.5, Playwright 1.64.1.

Движок выбирается после темы (например Phaser для 2D или Three.js для 3D).
React, сервер, БД и авторизация заранее не нужны без требований игры.

Команды из `.preparation/toolchain`:

```text
node secure-npm.cjs ci --no-fund
node secure-npm.cjs run check:versions
node secure-npm.cjs exec -- playwright install chromium
node secure-npm.cjs run check:browser
```

`secure-npm.cjs` включает проверку TLS для дочернего npm, потому что в родительском окружении обнаружен NODE_TLS_REJECT_UNAUTHORIZED=0. Глобальные настройки не изменены. Не отключать проверку сертификатов при ошибке сети.
Проверка браузера — лишь проверка инструмента, не тест игры. Vitest установлен, игровые тесты ещё не написаны.

## Публикация: рекомендация GitHub Pages

Бесплатно на GitHub Free для публичного репозитория. Изменение видимости пользователь делает сам; агент этого не делал.
Подходит для статической браузерной игры; серверный API и БД на Pages не работают.
Ожидаемый адрес после настройки: https://victorQA74.github.io/sharrowkin_game_jam/ — сейчас не подтверждён как работающий.

После темы и первой рабочей версии:
1. Проверить доступ и содержимое указанного репозитория.
2. В Vite установить base: '/sharrowkin_game_jam/'.
3. В GitHub Settings → Pages → Source выбрать GitHub Actions.
4. Создать workflow: npm ci → проверка типов → тесты → сборка → загрузка dist → deploy-pages.
5. Использовать встроенный GITHUB_TOKEN и минимальные права contents: read, pages: write, id-token: write. Личный токен для обычного Pages workflow не нужен.
6. Перед релизом проверить ссылку без входа в аккаунт, пути ресурсов, ввод, звук, победу/проигрыш и рестарт.
7. Сохранить стабильный коммит. Откат — повторный деплой известной рабочей версии, не переписывание истории.

Подготовлен неактивный шаблон `.preparation/templates/pages.yml.example`, не workflow в `.github`. После темы адаптировать под реальные команды приложения и перенести в `.github/workflows/pages.yml`. Запуск только вручную; публикация не выполнялась.

## Раздел 8 — не дать агенту забыть устройство проекта

Decision Log: короткая запись «что решили, почему, чем пожертвовали» для существенных решений.
Code Map: список модулей и ответственности — например, где ввод, состояние игры и отрисовка. Создавать после появления кода, не выдумывать архитектуру заранее.
Техдолг: известные недоделки записывать явно; не говорить «готово», скрывая отсутствующие функции. Не требуется документировать каждую строку.
